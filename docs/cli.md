# Справочник CLI

## Переменные окружения

```bash
cp .env.example .env
$EDITOR .env
```

| Переменная | Обязательна | Назначение |
|---|---|---|
| `RUTRACKER_USER_AGENT` | только обычный HTTP-режим | User-Agent браузера, из которого взяты cookies; с `--flaresolverr` определяется автоматически |
| `RUTRACKER_COOKIES` | нет | путь к Netscape-файлу, по умолчанию `./cookies.txt` |
| `RUTRACKER_BASE_URL` | нет | зеркало, по умолчанию `https://rutracker.net` |
| `RUTRACKER_USERNAME` | нет | только для `--login` (fallback, если challenge снимут) |
| `RUTRACKER_PASSWORD` | нет | то же |

`.env` и `cookies.txt` в `.gitignore`; учётные данные в коде не хранятся.

## Флаги

| Флаг | Смысл |
|---|---|
| `--query` | поисковый запрос (обязателен, кроме режима `--from-html`) |
| `--output` | каталог для `.torrent`, по умолчанию `./output` |
| `--from-html` | офлайн-режим: разобрать сохранённые страницы выдачи вместо запросов к сайту |
| `--links-out` | куда записать ссылки в режиме `--from-html`, по умолчанию `<output>/links.txt` |
| `--import-downloads` | разложить скачанные браузером `.torrent` по схеме именования проекта |
| `--dry-run` | только показать подходящие раздачи |
| `--verbose`, `-v` | подробный лог в stderr |
| `--delay` | пауза между запросами, по умолчанию 0.01 с с джиттером; не может быть отрицательной |
| `--max-pages` | предохранитель на обход выдачи, по умолчанию 50; не меньше 1 |
| `--concurrency` | одновременных запросов (обход выдачи и скачивание), по умолчанию 20; не меньше 1 |
| `--include-unknown` | качать и раздачи без книжных и аудио-маркеров |
| `--base-url` | другое зеркало |
| `--flaresolverr [URL]` | сессия через локальный FlareSolverr; URL по умолчанию `http://127.0.0.1:8191` |
| `--cookies` | путь к файлу cookies |
| `--login` | логин по паролю вместо cookies (сейчас упирается в challenge) |

Троттлинг общий для клиента: суммарная частота ограничена `1/--delay` независимо
от `--concurrency`. При дефолтном `--delay 0.01` практическим ограничителем
становится `--concurrency`. Поднимать `--concurrency` при большом `--delay`
бессмысленно — запросы всё равно будут сериализованы троттлингом.

Некорректные `--delay`, `--max-pages` и `--concurrency` отклоняются до первого сетевого запроса.

## Коды возврата

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | ошибка конфигурации или доступа (нет `RUTRACKER_USER_AGENT`, нет `cookies.txt`, неудачный логин) |
| `2` | сетевая ошибка, Cloudflare-challenge или протухшая сессия |
| `3` | прогон дошёл до конца, но были ошибки скачивания отдельных раздач |
| `4` | ошибка файловой системы (нет прав на каталог вывода, кончилось место) |

При аварийной остановке статистика за уже пройденную часть прогона всё равно
печатается.

## FlareSolverr

```bash
docker compose up -d
uv run --extra flaresolverr python -m rutracker_downloader \
    --flaresolverr --query "кант" --output ./torrents/kant \
    --delay 1 --concurrency 2
```

Нужны Docker Compose и Netscape-файл cookies с действующим
`bb_session`. `--cookies` и `RUTRACKER_COOKIES` задают именно исходный файл:
в этом режиме кэш обычного HTTP-клиента не используется. Значение User-Agent
для сетевых запросов берётся из ответа FlareSolverr; задавать
`RUTRACKER_USER_AGENT` в `.env` для этого режима не требуется.

При каждом запуске FlareSolverr получает первую страницу и новую сессию,
используя браузер в фоне. Далее запросы выполняет `curl_cffi` с профилем
`chrome146`. Сессия хранится только в памяти. Cookies других доменов не
передаются сервису. Допускаются только локальные URL сервиса без пути;
`--base-url` должен использовать HTTPS. Перенаправления на другой origin
отклоняются.

На получение сессии отводится 60 секунд; недоступность сервиса, некорректный
ответ и challenge дают код `2`. Если challenge появляется позднее, прогон
завершается после текущей группы задач: повторный запуск получает новую
сессию и пропускает уже сохранённые файлы. Автоматического обновления сессии
посреди прогона нет. `--login` и офлайн-флаги несовместимы с `--flaresolverr`.

При другом локальном порте: `--flaresolverr http://127.0.0.1:18191`.
Остановка: `docker compose down`. После обновления браузера FlareSolverr
совместимость профиля curl необходимо перепроверить; Compose закрепляет
проверенный образ по digest.

## Офлайн-режим: браузер как транспорт

Cloudflare привязывает `cf_clearance` к отпечатку клиента, прошедшего проверку.
Cookie, выданная Firefox (TLS-стек NSS), из `httpx` (OpenSSL) уже не
принимается — это штатное поведение механизма, а не сбой, и переэкспорт cookies
его не обходит (подробности в `docs/authentication.md`). Поэтому запросы делает
сам браузер, а утилита берёт разбор, фильтрацию и именование.

### Шаг 1. Обход выдачи из браузера

Один раз выключить HTTP/3: `about:config` -> `network.http.http3.enable` ->
`false`, перезапустить Firefox. Иначе RuTracker отдаёт заголовки, но тело
ответа обрывается, и файлы приходят нулевого размера.

Открыть выдачу `https://rutracker.net/forum/tracker.php?nm=<запрос>`, нажать
F12, вкладка «Консоль», вставить целиком `scripts/browser_fetch.js` и нажать
Enter. Скрипт обойдёт все страницы выдачи и скачает все `.torrent`, ничего не
фильтруя, с паузой в секунду между запросами.

В каталоге загрузок появятся `rutracker-page-NN.html` и `<topic_id>.torrent`.

### Шаг 2. Разбор и раскладка

```bash
uv run python -m rutracker_downloader \
    --from-html ~/Downloads/rutracker-page-*.html \
    --import-downloads ~/Downloads \
    --output ./torrents/kant
```

Фильтры применяются здесь: скачанное сниппетом «всё подряд» раскладывается
только в части, прошедшей отбор. Остальное остаётся в загрузках нетронутым.
Правила отбора те же, что и в сетевом прогоне — общий `select_entries`.

Скачивать выдачу целиком не жалко: `.torrent` весит 2-30 КБ. Зато фильтрация
остаётся в одном месте: копия правил в JS неизбежно разошлась бы с
`filters.py`.

### Только список ссылок

Без `--import-downloads` режим `--from-html` просто пишет отфильтрованный
список ссылок в `<output>/links.txt` — для внешней качалки:

```bash
uv run python -m rutracker_downloader --from-html ~/Downloads --output ./output
```

Аргументом может быть каталог (разворачивается в `.html`/`.htm` внутри него,
в отсортированном порядке) или перечисленные файлы. Кодировка определяется
сама: `cp1251` как у самого форума и `utf-8`, если страницу сохранил
инструмент с конвертацией.

Сеть в этом режиме не используется вообще, поэтому не нужны ни `cookies.txt`,
ни `RUTRACKER_USER_AGENT`. С `--dry-run` вместо файла печатается список.

Если сохранённая страница не дала ни одной раздачи, в лог идёт предупреждение:
чаще всего это случайно сохранённая страница проверки Cloudflare или страница
гостя.

## Импорт скачанного (`--import-downloads`)

Браузер сохраняет `.torrent` под именем из `Content-Disposition`
(`<название> [rutracker.net].t<id>.torrent`), но обрезает его по 255-байтному
пределу файловой системы — и обрезается как раз хвост с `topic_id`. Поэтому
`topic_id` берётся не из имени, а из полей `comment` / `publisher-url` внутри
самого файла: там лежит адрес темы.

```bash
uv run python -m rutracker_downloader \
    --from-html ~/Downloads/pages \
    --import-downloads ~/Downloads \
    --output ./output
```

`--from-html` здесь нужен только ради названий раздач: без него имя выйдет из
одного `topic_id` (`6886527.torrent`), что тоже рабочий вариант.

Файлы нулевого размера и всё, что не проходит проверку `is_torrent_payload`,
пропускаются с предупреждением и попадают в счётчик ошибок — код возврата
станет `3`. Это нормально, если в каталоге лежат остатки оборвавшихся загрузок.

Раскладка идемпотентна: повторный запуск не перезаписывает уже разложенные
файлы, а считает их как «уже существовало».

### Если `.torrent` не скачивается браузером

Проверено на этой машине: при включённом HTTP/3 RuTracker отдаёт заголовки, но
тело ответа обрывается — файл создаётся нулевого размера. Лечится в
`about:config`: `network.http.http3.enable` → `false`, затем перезапуск
браузера.
